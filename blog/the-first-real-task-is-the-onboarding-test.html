The first real task is the onboarding test.

Published November 3, 2026

Onboarding can look complete long before a new teammate can work. They have the folders, the welcome call, perhaps a careful tour of the process. Then a real task arrives and the useful question is not “where is the documentation?” It is “which part of this history is current enough to govern what I do next?”

If the answer requires a senior colleague to translate the chat archive, onboarding has transferred material without transferring a working path. The folder is not the memory. The narrator is doing the retrieval.

Run the test on one task, not the whole organisation

Choose a task a new teammate actually has to perform this month. It might be responding to a service request, preparing a client handover, changing a deployment setting, or handling an approval. Ask three questions before you call them ready:

  1. What outcome is this workflow meant to produce? A task without an intended result is just a sequence of inherited motions.
  2. Which source and decision govern it now? Not every link in a folder has equal authority. The person doing the work needs to know what is current, and why.
  3. Where does the reviewed lesson return when the task is done? If the first real use exposes an exception or a better path, the next person should not have to rediscover it from a private message.

This is deliberately smaller than a transformation programme. It does not promise that a new person will become productive by magic. It asks whether the team can provide the context a real task needs: an outcome, a governing source and decision, and a place for the next reviewed lesson.

Why the first task tells the truth

Checklists are easy to complete because they mostly ask whether information was handed over. Real work tests whether that information can be retrieved inside the right scope. A new teammate may need the current procedure but not another customer’s context. An approved AI tool may need the same standard without inheriting every private conversation around it. That is a memory design problem, not a motivation problem.

Usable publicly describes a governed home for procedures, decisions, files, and reusable context. Its public workflow includes separate workspaces, access boundaries, retrieval that brings the source back, and solution writeback for reviewed lessons. Those are useful primitives for this test: give the task its context inside the appropriate boundary, then improve what the next task can retrieve.

Pick one first task. Can a new teammate identify its outcome, retrieve the governing source and decision in the right boundary, and return a reviewed lesson when reality disagrees?
