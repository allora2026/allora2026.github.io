A standard is not available just because it exists.

Published October 13, 2026

A deployment rule may be versioned and approved yet still fail the moment work starts. If the engineer or authorized tool cannot find the authoritative source, establish that it applies to this repository and environment, and route a discovered exception into review, the rule is stored—not operationally available.

This is the quiet failure mode behind a great deal of technical rediscovery. Teams call the rule documented because it exists in a repository, ticket, wiki, or the head of the last responder. Then an incident, implementation, or deployment starts somewhere else. The task has an answer-shaped gap, and the team fills it with chat search, confidence, or luck.

Run a pre-change check

Before a deployment, incident response, or implementation begins, confirm three things. Not a grand framework. A check small enough to survive contact with the work.

  1. Authority. Which named runbook, decision, standard, or repository pattern governs this operation?
  2. Scope. Which repository, service, environment, or release makes that guidance applicable—and what would make it inapplicable?
  3. Repair path. If the work exposes an exception or gap, where does the proposed correction go for review?

“Documented” is a weak status

A standard earns a stronger status when it can be used at the moment of work. That does not mean every person or tool receives every source. It means the right source is reachable inside the right boundary, with enough context to avoid treating a local exception as a universal rule.

The receipt is deliberately plain because the alternative is too familiar: a technically plausible answer that quietly belongs to the wrong repository, environment, or team. Plausible is not the same thing as applicable. A clean answer with no source or scope is just a faster path to a repeatable mistake.

Make the next task cheaper to begin

The repair path matters because technical work changes the evidence. A solved incident may sharpen a runbook. An implementation may expose a missing assumption. A deployment may reveal that a rule needs a narrower boundary. If the outcome vanishes into the completed task, the next task pays to rediscover it.
