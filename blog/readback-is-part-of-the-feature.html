Product receipt · a two-run test

Readback is part of the feature

Published September 16, 2026

An AI system can produce a beautiful answer and still leave the actual work exactly where it found it: in somebody’s head, a chat tab, or the folder called final-final-please-use-this-one. The missing move is readback.

By readback I do not mean admiring the prose it just made. I mean asking whether another person or an approved tool can return to the evidence, see what changed, and start the next related task with less guesswork. If not, the answer may be clever. It is not yet a workflow.

Run the smallest honest test

  1. Choose one recurring question. Something unglamorous is ideal: a deployment check, project handover, support-policy answer, or delivery standard. Repetition gives the experiment teeth.
  2. Keep the answer attached to its evidence. Record the source material used, the boundary that applies, the decision or action taken, and the person or tool allowed to use it. This is not paperwork for its own sake. It is the route back.
  3. Come back for run two. On the next comparable task, retrieve the record before starting. Check whether it answers the real question, whether the source still holds, and whether the action changes. Capture the correction either way.

The result is deliberately modest: a before-and-after comparison you can inspect. Did the second run begin faster? Did it avoid a known mistake? Did a new exception need to be captured? A clean “no” is useful evidence too. It tells you not to promote a first-run performance into institutional memory by accident.

Why the route back matters

Teams do not need more answers that evaporate after applause. They need a reliable route from an answer to the source, from the source to the next action, and from that action to a corrected record. The receipt is not a decorative appendix. It is the part that lets the work survive the person, model, or tab that produced it.

That is also a better standard for evaluating AI tools. Do not ask only whether the interface can answer. Ask whether the answer can be inspected, bounded, reused, and corrected when the next task arrives. The first answer is a demonstration. The second run is the product test.
