The checklist is the demo

Published September 9, 2026

The most useful demo for AI memory is not a cinematic prompt. It is a checklist a real team can run against its own work without being seduced by the nearest sparkle cannon.

I built this one from public product material, not private customer proof: Usable describes itself as an organisational memory and AI knowledge base for teams, with workspaces, access boundaries, source-returning retrieval, Usable Chat, MCP, APIs, and solution writeback. That is enough to make a practical evaluation tool. No prophecy required. Small mercy.

Run this before you trust the memory

  1. Name the repeated work. Pick one recurring handover, service answer, deployment fix, onboarding explanation, client context packet, or standards decision. If nobody repeats it, the memory is decoration.
  2. Attach the source. The remembered answer should point back to a procedure, decision, file, runbook, or prior fix. If the source disappears, confidence should go with it.
  3. Set the boundary. Decide which workspace, team, customer, assistant, or product surface may use the context. Serious memory is not “everything for everyone.” That is just a breach with better branding.
  4. Ask from the place work happens. Test whether a person or approved AI tool can retrieve the right context through the interface it actually uses: browser chat, an MCP-compatible assistant, an API-backed workflow, or an internal app.
  5. Write the solved problem back. When the work improves, keep the new rule, exception, or fix as reusable memory. If every win dies in the transcript, the system is still making humans pay the tax twice.
  6. Check the second task. The honest proof is not the first answer. It is whether the next related task starts sharper because the previous one happened.

What makes the checklist hard

Each step sounds obvious until the boundary matters. A consultancy may need client knowledge reusable inside one engagement and invisible to another. A public body may need rules and prior decisions available to staff without turning sensitive context into ambient sludge. A DevOps team may need the incident fix available before the next deployment, not embalmed in a heroic postmortem nobody opens.

The checklist forces the useful questions: what work repeats, what source supports it, who may use it, where retrieval happens, what gets written back, and whether reuse changed a later task. That is less glamorous than a prompt trick. It is also harder to fake.

Where Usable fits

This is the bridge to Usable: a governed place for procedures, decisions, files, and reusable organisational context, with interfaces for people and approved AI tools. The product claim worth testing is not that memory exists. Memory always exists somewhere, usually in three inboxes and one tired colleague’s head.

The claim worth testing is whether your team can store what matters, control who can use it, retrieve the source when work demands it, and write the solved problem back so the next task starts less stupid. If that checklist describes a pain you actually have, start there. Try one workflow. Keep the receipt. Then ask whether the second task got better.
