The before-work receipt is a question, not a form.

Published October 14, 2026

The worst possible time to discover that a rule is ambiguous, unavailable, or meant for another environment is after someone has started changing the system. Yet teams routinely call that discovery “execution.”

A before-work receipt is a small interruption designed to prevent that category error. It is not a compliance ritual and it does not certify that a change will succeed. It asks whether this task has the context required to begin honestly.

Four answers before the first command

  1. What task is about to begin? Name the deployment, incident response, implementation, or investigation in plain terms.
  2. Which source is authoritative? Point to the decision, runbook, standard, or prior fix—not a memory of one.
  3. Which boundary applies? Establish the repository, service, environment, team, or access boundary that makes the source relevant here.
  4. Where will the next lesson go? If the work changes what the team knows, name the reviewed capture point before the evidence scatters.

The questions are intentionally modest. They do not turn a runbook into automatic enforcement, and they do not make every answer universally available. They expose the missing context early enough for someone to retrieve it, narrow it, or ask for a review.

The form is not the point

A filled-in template with no reachable source is theater. So is a polished answer with no indication of where it applies. The receipt earns its name only when it changes the start of the work: the responsible person or approved tool can find the source permitted for this task, see its scope, and preserve a verified correction when the work teaches something new.

That is why a technical workflow needs more than a folder of documents. It needs a route from a live task to governed source material, then back to a reviewable place where the outcome can help the next task. Otherwise the team has records, but not usable operating context.

Start small enough to repeat

Try the receipt on one recurring task this week. Do not grade the team on whether every answer is perfect. Notice which answer is difficult to produce. That difficulty is a map: perhaps the source is scattered, perhaps the boundary is unclear, perhaps lessons have no home after the work closes.

The useful promise is narrower than magic: the next task does not have to begin by pretending it knows what the last one learned.

Run the receipt once
